# Crabby — Design System

> **Document status:** Planning draft. Tokens are proposed values, chosen for legibility on phone screens and in
> terminals — not a brand exercise. Screen structure belongs to `docs/UI_UX_SPEC.md`.
>
> **Review status:** per D-055 this file is regenerated from the element inventories in `docs/review/` once those are
> approved; the palette and type values below are candidates until that pass, **except §2.3**, whose values were
> measured and accepted on 2026-10-10 (D-068 closing O-044, O-045, O-046). Type sizes and spacing rhythm are still
> candidates: they need the phone in front of them (O-006), and no arithmetic can substitute for that.

## 1. Principles

01. **Legible at arm's length.** The default case is a phone in daylight, not a studio monitor.
02. **Dark-first, light-supported.** A Gateway left running on a phone is usually looked at in a dark terminal;
   dark must be a designed theme, never an inverted one.
03. **Two terminals, one system.** Web and TUI share tokens semantically (same color for the same tier, same
   spacing rhythm) even though the Web UI has more expressive power.
04. **Battery and bandwidth are design constraints.** Large images, gradients used decoratively, and continuous
   animation are all costs on the primary device.
05. **No dependency required to be consistent.** Tokens are plain values in one file. The Web UI builds its own
   primitives (D-068, closing O-043), so nothing in this system may assume a component library — not "not yet", but
   "not, by design".
06. **Meaning never travels by color alone** (`docs/UI_UX_SPEC.md` §9).

## 2. Color

### 2.1 Roles, not raw hexes

Semantic tokens first. Concrete values are in §2.3, with their measured ratios (O-044 closed by D-068). The constraints below are
what those values have to satisfy, and they are checked by `scripts/check-docs.py` rather than reviewed by eye.

| Token | Role | Constraints |
| --- | --- | --- |
| `bg.base` `bg.raised` `bg.overlay` | Surfaces, three levels only | Level changes by subtle steps; more than three levels is noise on a small screen |
| `fg.primary` `fg.secondary` `fg.muted` | Text | ≥4.5:1 on `bg.base`; `fg.muted` ≥3:1 minimum, measured at 4.5 in §2.3, and never used for required information |
| `accent` | Interactive/selected | One accent. A second decorative accent is out of scope for v1 |
| `state.ok` | Success | Must remain distinguishable without hue |
| `state.warn` | Needs attention (partial compatibility, expiring approval) | |
| `state.err` | Failure, denial | |
| `state.info` | Neutral progress | |
| `risk.t0` … `risk.t3` | Tier chips | Monotonic visual weight: as risk rises, saturation and icon complexity both rise. `t3` is the only tier allowed a background fill |
| `diff.add` `diff.del` | File previews | Colorblind-safe pairings, never red/green alone |
| `tunnel.on` | Remote exposure indicator | Reserved color; nothing else may use it, because it is the one state a user must never confuse |

### 2.2 Dark and light

Both themes define the same token names. Light is not generated by inversion. Focus rings, selection, and
streaming-cursor colors are specified per theme rather than inherited, since contrast failure hides in those three.

Three consequences of actually measuring, recorded because each one contradicts something that looked obvious:

01. **Light is not an inverted dark.** The first light `fg.muted`/`accent` candidate pair passed on `bg.base` and
    **failed on `bg.raised`** (4.19 and 4.47 against a 4.5 floor). Choosing per theme is not a style preference; it is
    what the arithmetic forces.
02. **No hue pair in this palette can carry the diff meaning alone.** The best luminance separation between two state
    colors that *both* clear 3:1 on every surface is 17% (green/red), while the "colorblind-safe" blue/orange pairing
    separates by 7% and teal/orange by 2%. So the `+`/`-` prefixes, the tier labels and the words are the meaning, and
    color is decoration — this is the measured basis for §1's never-color-only rule, not a typographic taste.
03. **`fg.muted` clears 4.5 in both themes**, which is stricter than the old "≥3:1 and never for required
    information" line required. Muted text that is also unreadable is how a screen reader of the eye works; the
    "never required information" rule stays on top of the ratio, not instead of it.

## 3. Typography

| Token | Use | Notes |
| --- | --- | --- |
| `font.ui` | Interface text | System stack: `ui-sans-serif, system-ui, Roboto, "Noto Sans Bengali", sans-serif`. No webfont download on first paint — on a metered phone connection that is a real cost, and system Bengali shaping is better than a partial fallback. |
| `font.mono` | Code, tool output, ids, commands | `ui-monospace, "SF Mono", Menlo, Consolas, "DejaVu Sans Mono", monospace`. `JetBrains Mono`/`Fira Code` are optional upgrades, never required — a phone terminal may not have them. |
| `size.xs … size.xl` | 6 steps max | Body 15–16px in Web, no size below 13px, since 12px on a phone is a support ticket. |
| `lh.tight` `lh.normal` `lh.loose` | 1.25 / 1.5 / 1.7 | `lh.normal` for Bengali, which needs more leading than Latin at the same size. |
| `weight.regular` `weight.medium` `weight.semibold` | Three only | Bold is reserved for state changes and approvals, not for decoration |

Rules: tabular numerals for timings and token counts; `text-wrap: balance` on short headings; never uppercase long
labels (Bengali has no case, so uppercase styling silently becomes Latin-only design); no letter-spacing on
non-Latin text; line length capped at ~72ch in chat.

## 4. Spacing and Layout

- 4px base unit; scale `4 8 12 16 24 32 48`. No off-scale values.
- Component padding is defined by these steps only; a component that cannot fit them is sized wrong.
- Web breakpoints: `360` (design case) · `600` · `960` · `1280`. The 360 layout must be complete, not a squeezed
  desktop one.
- Safe-area insets are honored (notched phones) for the bottom bar and modal actions (`docs/UI_UX_SPEC.md` §2).
- Terminal rhythm: TUI uses the same scale expressed in character cells — 1 blank line between blocks, never 2;
  2-space indent inside tool output.
- Max content column in chat: 72ch; on wide screens the panel is centered rather than stretched edge to edge.

## 5. Iconography and Symbols

| Symbol | Meaning | Fallback on limited terminals |
| --- | --- | --- |
| `●` | running | `( )` |
| `✓` `✗` | ok / failed | `ok` / `err` |
| `▶` `⏸` `⏹` | start / paused / stopped | `>` `\|\|` `x` |
| `⚠` | needs attention | `!` |
| `🔒` `🔓` | vault locked / unlocked | `locked` / `unlocked` |
| `⇅` | reconnecting | `~` |

Rules: one stroke weight; icons never convey a state alone (always paired with a label in v1); no emoji in
machine-facing output; icon-only buttons require a tooltip and an accessible name.

## 6. Components

Each component lists contract, states, and the shared behavior it must not improvise.

| Component | Contract | States |
| --- | --- | --- |
| `Button` | variants `primary` `secondary` `danger` `ghost`; min height 44px on touch | default, hover, focus-visible, active, disabled, pending |
| `IconButton` | accessible name required, ≥44px hit area | as above |
| `TextField` | label above, helper below, error replaces helper (never sits beside it) | empty, typing, error, disabled |
| `Chip` | used for model, tier, source, platform; click-to-filter only when a filter exists | default, selected, disabled |
| `TierChip` | `T0`…`T3` + color + label, non-negotiable triple | — |
| `Card` | one heading, one primary action, one or two meta lines; no nested cards | default, attention, disabled |
| `TaskCard` | title, state chip, measured-vs-estimated progress, model + provider, pending-approval badge | queued, planning, running, awaiting approval, cancelling, terminal |
| `StepList` | ordered steps with dependencies shown; per-step tool + tier + duration | pending, running, done, failed, blocked, skipped |
| `ToolCallRow` | collapsed: tool name, tier, status, duration. Expanded: args (secrets redacted), output (truncated with a marker), errors | running, ok, failed, blocked-by-policy |
| `ApprovalDialog` | action summary, exact target, consequence, reversibility, expiry countdown, approve-once / deny | pending, expired, answered-elsewhere, conflict |
| `StreamCursor` | inline block at the end of streamed text; hidden when the stream stalls, replaced by "no output for Ns" | streaming, stalled |
| `Banner` | page-level, dismiss only when it will recur | info, warn, error, tunnel-active |
| `Modal` / `Sheet` | focus trapped; destructive action never pre-focused; sheet for mobile, modal for ≥960 | open, closed |
| `Table` | sticky header on desktop, card-stacks on narrow; horizontal scroll only as a last resort | empty, loading |
| `JsonView` | syntax-highlighted, collapsed past 40 lines, copy button | truncated, redacted |
| `DiffView` | split or unified toggle at ≥600px, unified only below | — |
| `ModelPicker` | grouped by provider; shows overrides applied, capability gaps, and cost class | loading, none-configured |
| `ProviderForm` | base URL + model names + vault-referenced key; "test connection" inline | editing, validating, ok, error |
| `CapabilityMatrix` | reported vs effective with override controls (per-model) | — |
| `ExtensionCard` | source tier, verdict, capability grants, conversion-report link | compatible, partial, incompatible, quarantined |
| `ConversionReport` | mapped / dropped / reinterpreted / unknown, with diff against previous version (D-039) | — |
| `CodeBlock` | copy, wrap toggle, mono only, line numbers off by default | truncated, redacted |
| `EmptyState` | one sentence + one action (`docs/UI_UX_SPEC.md` §2.3) | — |
| `ErrorPanel` | `code`, human line, what completed, what is pending, resumable?, request id | — |
| `Toaster` | non-blocking only; anything requiring a decision uses a Banner or Modal | — |

Shared behavior: focus order matches reading order; every async control shows a pending state instead of looking
dead; redaction is rendered with a visible "redacted" marker so users learn to trust it; copyable values are copy
targets, not text to highlight manually.

## 7. Motion

- Durations `120ms` / `180ms` / `240ms`, ease-out for entry, ease-in for exit. Nothing loops for decoration.
- Streaming is not animated: text appears as it arrives. Animating incoming tokens costs battery and hurts
  readability on a phone.
- Progress changes are allowed a short transition; a task state change is *not* allowed to animate long enough to
  hide a cancellation.
- `prefers-reduced-motion` reduces to instant; the documented low-resource mode disables transitions entirely
  (`SECURITY.md` §12).

## 8. Data Density Modes

| Mode | Effect | When |
| --- | --- | --- |
| `comfortable` | default desktop | |
| `compact` | one-line rows, hidden meta, tighter spacing | narrow screens, long task lists |
| `reduced` | no transitions, lower event render rate, tool output collapsed | low-resource devices or user preference |

Density is a user setting per interface, stored in configuration — never auto-detected and changed silently,
because a UI that shifts under the user reads as a bug.

## 9. Token Delivery

- One source of truth: `packages/ui-tokens` exposing CSS custom properties, and the same values mapped to ANSI
  colors + attributes for the TUI (`ARCHITECTURE.md` §18).
- The TUI may only use what a real terminal supports: 16-color and 256-color paths are both required, with a
  legible 8-color fallback rather than a broken one.
- Tokens are not re-derived per component; a component needing a new value means a token is missing, and the token
  gets added here first.
- No theme file inside an interface app; themes live with the tokens so Web and TUI cannot drift.

## 10. Open Decisions

Recorded in `DECISIONS.md`: ~~**O-043**~~, ~~**O-044**~~, ~~**O-045**~~ and ~~**O-046**~~ are **closed by D-068** —
the Web UI builds its own primitives, the palette has measured values in §2.3 that the checker recomputes, both
themes ship in v1, and TUI color capability is a user setting with a `$COLORTERM` default and a legible 8-color tier.
What is *not* decided by that: how the type scale reads on the target phone at arm's length (O-006), which is a
measurement and stays one.

## 11. Acceptance Criteria

01. Every token in §2–§4 exists in code as a single shared source, with no hardcoded values in interface apps.
02. The palette passes WCAG 2.2 AA for text and non-text contrast at 360px, verified, not eyeballed.
03. Every §6 component has a documented state list and a rendering test at narrow and wide sizes.
04. Tier, risk, and connection state survive grayscale printing — no meaning carried by hue alone.
05. TUI has a working 8-color fallback path.
06. Bengali text is rendered and reviewed in both dark and light themes before any string is called final.
